# Database schema

## 2026-10-24 event 17135 MATCH/GROW reset

Before the authorized reset, `dashboard_aggregates` held 9 completed meetings, 3 feedback submissions, and rating sum 12. The linked database held 11 `meeting_records`, 3 `feedback_records`, 10 `controller_requests`, and 2 existing `controller_reversals`; only unreversed actions contributed to the aggregate. The meeting/feedback rows reference `(event_id, request_id)` in `controller_requests`, and reversals reference the original request with a unique `(event_id, original_request_id)` constraint. Deleting records while retaining requests or cached totals would have broken the audit and correction contract.

The reset used one guarded PostgreSQL transaction for event 17135. It first ran with `ROLLBACK`, then committed exactly eight calls to the existing service-only `reverse_controller_action` RPC, one per active original request, with reason `other`. The RPC locked each original request, checked its retained records and staff membership, subtracted its contribution from `dashboard_aggregates`, and inserted an immutable reversal. No meeting, feedback, controller request, or pre-existing reversal row was deleted. Postconditions inside the transaction required 0 meetings, 0 feedback, 0 rating sum, and no active requests; they also required the original MEET counts and publication timestamp. Retries of those original request IDs return their existing result, and the unique reversal constraint prevents an old action from contributing again. A fresh hosted read confirmed 0/0/0 and unchanged MEET 202/0 with the same timestamp.

The authorized controller test then added one +1 meeting and one 5-star rating, observed the dashboard at MATCH 1 and GROW 1 / 5.0, and reversed both through `/controller`. Final hosted state is `completed_meetings=0`, `feedback_count=0`, `rating_sum=0`, with no active meeting or feedback requests. Physical audit totals are now 12 meeting records, 4 feedback records, 12 controller requests, and 12 reversals; these retained rows do **not** contribute to current totals. `meet_snapshots` remains one row, with zero `sync_runs` and `sync_leases`. This is an audited reset; restoring old counts would require a separately reviewed forward correction, not removal of reversal history. No schema, auth, map, or other event data was changed.

The versioned migrations `20261013191540_initial_dashboard_schema.sql`, `20261014201641_restrict_rls_auto_enable_execute.sql`, `20261015204348_audit_controller_reversals.sql`, and `20261023000100_map_dashboard_snapshots.sql` are applied to linked controlled test project `kkiambvltxuieuncwtfz`. The first was applied on 2026-10-14; the next two were owner-approved and pushed on 2026-10-16 after a rollback-only SQL probe and backup snapshot; the map migration was approved and applied on 2026-10-23. Every event-scoped table is constrained to event 17135 through `event_settings`. No b2match participant ID, check-in history, name, email, phone, or answer is stored.

All new tables have RLS enabled. `anon` has SELECT only on the public map aggregate and no grant on the private dashboard/controller tables. `authenticated` has SELECT grants on membership, settings, dashboard aggregate, and map aggregate tables, each with event/identity policies. The service role alone can write. Public RPC functions use `SECURITY INVOKER`, have `EXECUTE` revoked from `PUBLIC`, `anon`, and `authenticated`, and are granted to `service_role` only. The `dashboard_aggregates` table alone is added to the `supabase_realtime` publication; a hosted query found zero publications for `map_dashboard_snapshots`. No private records are broadcast.

`claim_meet_sync` creates a run and acquires/replaces only an expired lease. It marks an expired abandoned run as failed and flags the prior MEET aggregate as stale. `complete_meet_sync` checks the active token, expiry, and running status, then inserts the new snapshot, updates the display aggregate, marks the run successful, and releases the lease in one PostgreSQL transaction. An expired old run cannot overwrite a newer one. `fail_meet_sync` first verifies and locks the matching lease, then records a safe error class and failure timestamp without changing the last successful counts. A wrong or replaced token cannot mark an active run as failed. A later database outage during failure recording still leaves the last successful snapshot unchanged.

The 2026-10-21 local sync repair changes no schema or grants. The Edge function now withholds `complete_meet_sync` when the shared verification summary flags an unrelated event entrance or unknown participant status. It sends completed page/record progress to `fail_meet_sync` for post-fetch validation failures. The transaction boundary and lease logic above are unchanged. Read-only hosted catalog checks confirmed RLS on the five sync/settings/aggregate tables, service-only execution of the three sync RPCs, and zero sync runs or leases. Transactional behavior was not rerun because this task was restricted to read-only hosted tests.

`record_meetings` and `record_feedback` verify the staff membership again in SQL. Their event/request-ID uniqueness and row locks make retries safe under concurrent calls. They insert individual records and update the aggregate in the same transaction. The aggregate constrains rating sums to the 1–5 range implied by the feedback count. The schema defaults the meeting target to null; the client confirmed 1,200 on 2026-10-15, and only `event_settings.meeting_target` was set to 1,200 for event 17135. The actual completed-meetings aggregate was not changed by that setting update.

`20261015204348_audit_controller_reversals.sql` adds the reversal audit table, a recent-request index, and service-only `reverse_controller_action` / `list_controller_actions` RPCs. A reversal locks its original request, checks staff membership and retained individual records, subtracts the full original quantity or rating contribution atomically, then inserts one uniquely keyed audit row. Exact retries return the existing reversal; another correction for that action fails. Ordinary reversals retain original requests and meeting/rating records. Only `dashboard_aggregates` remains in the Realtime publication.

The security migration conditionally revokes `EXECUTE` on the pre-existing `public.rls_auto_enable()` from `PUBLIC`, `anon`, and `authenticated`. After deployment, hosted grant checks found `anon` and `authenticated` could not execute the helper and the trigger remained enabled; `service_role` retained access to the new correction RPCs while browser roles did not.

Retention is not yet approved. The current schema retains safe aggregate snapshots, sync metadata, and staff action records until an owner-approved retention and deletion procedure is set. Before production release, run full security/performance advisors with project access, test simultaneous sessions and Realtime delivery, and rehearse backup and rollback. Never reset a hosted database to test this migration.

## Pending migration: manual check-in accounting

`20261023172257_manual_checkin_fallback.sql` adds `meet_checkin_control` (API/manual mode, session ID, baseline and start time), extends `controller_requests` with `checkin` and its manual session ID, and adds immutable `checkin_reconciliations` audit rows. RLS is enabled on new tables; browser roles receive no grants. `record_manual_checkin` locks the event control and aggregate, enforces staff membership, a unique request ID and registered-capacity bound, then increments the effective aggregate and percentage atomically. `reverse_controller_action` retains its original audit row and decrements an eligible active-session +1 in the same transaction. A reconciled session's manual operations stay in history but cannot later alter the API-derived count.

`complete_meet_sync` retains raw API measurements in `meet_snapshots`. During manual mode it updates registration and freshness but preserves effective checked-in and recalculates the percentage; it rejects an API registration count below the current effective check-ins. `reconcile_manual_checkins` requires a newer raw snapshot plus exact expected counts/time, records the actor and both totals, then switches the effective count to the reviewed API count. This explicit replacement handles aggregate overlap without adding raw and manual totals. `list_controller_actions` returns five chronological operations from original requests, reversals, and reconciliations. Historical rows are retained. The migration is local and unapplied; reversing it after use would require preserving/exporting the audit and effective-count state rather than dropping data.
