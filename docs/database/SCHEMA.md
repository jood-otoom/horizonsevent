# Database schema

## Historical 2026-10-24 event 17135 MATCH/GROW reset

Before the authorized reset, `dashboard_aggregates` held 9 completed meetings, 3 feedback submissions, and rating sum 12. The linked database held 11 `meeting_records`, 3 `feedback_records`, 10 `controller_requests`, and 2 existing `controller_reversals`; only unreversed actions contributed to the aggregate. The meeting/feedback rows reference `(event_id, request_id)` in `controller_requests`, and reversals reference the original request with a unique `(event_id, original_request_id)` constraint. Deleting records while retaining requests or cached totals would have broken the audit and correction contract.

The reset used one guarded PostgreSQL transaction for event 17135. It first ran with `ROLLBACK`, then committed exactly eight calls to the existing service-only `reverse_controller_action` RPC, one per active original request, with reason `other`. The RPC locked each original request, checked its retained records and staff membership, subtracted its contribution from `dashboard_aggregates`, and inserted an immutable reversal. No meeting, feedback, controller request, or pre-existing reversal row was deleted. Postconditions inside the transaction required 0 meetings, 0 feedback, 0 rating sum, and no active requests; they also required the original MEET counts and publication timestamp. Retries of those original request IDs return their existing result, and the unique reversal constraint prevents an old action from contributing again. A fresh hosted read confirmed 0/0/0 and unchanged MEET 202/0 with the same timestamp.

The authorized controller test then added one +1 meeting and one 5-star rating, observed the dashboard at MATCH 1 and GROW 1 / 5.0, and reversed both through `/controller`. The post-test state at that time was `completed_meetings=0`, `feedback_count=0`, `rating_sum=0`, with no active meeting or feedback requests. At that historical checkpoint, physical audit totals were 12 meeting records, 4 feedback records, 12 controller requests, and 12 reversals; those retained rows did **not** contribute to the totals then. `meet_snapshots` still held one row, with zero `sync_runs` and `sync_leases`. This was an audited reset; restoring old counts would require a separately reviewed forward correction, not removal of reversal history. No schema, auth, map, or other event data was changed.

The versioned migrations `20261013191540_initial_dashboard_schema.sql`, `20261014201641_restrict_rls_auto_enable_execute.sql`, `20261015204348_audit_controller_reversals.sql`, and `20261023000100_map_dashboard_snapshots.sql` are applied to linked controlled test project `kkiambvltxuieuncwtfz`. The first was applied on 2026-10-14; the next two were owner-approved and pushed on 2026-10-16 after a rollback-only SQL probe and backup snapshot; the map migration was approved and applied on 2026-10-23. Every event-scoped table is constrained to event 17135 through `event_settings`. No b2match participant ID, check-in history, name, email, phone, or answer is stored.

All application tables have RLS enabled. The event-controls migration grants `anon` SELECT on event 17135's safe `dashboard_aggregates` row to support the public Realtime subscription. It contains counts and freshness timestamps only. The public display's HTTP payload continues through `public-dashboard-data`. Private control state, synchronization errors, raw snapshots, staff audit rows and configuration remain inaccessible to anonymous clients. `authenticated` retains member-scoped SELECT on membership, settings and aggregates; direct client writes remain denied. The service role alone invokes public mutation RPCs, all `SECURITY INVOKER`, revoked from `PUBLIC`, `anon` and `authenticated`. Only `dashboard_aggregates` is in the Realtime publication; neither private control/audit rows nor map rows are broadcast.

After the event-controls migration, `claim_meet_sync` accepts only an enabled API-mode event whose next 120-second due time has arrived and has no lease. It stores the current generation in `sync_runs`, records attempt time and the next due time, then creates a 150-second lease. `complete_meet_sync` locks the same control row, checks mode, enabled state, generation, run status, matching token and expiry, then publishes the complete snapshot/aggregate and releases the lease atomically. `fail_meet_sync` stops synchronization, advances the generation, clears the next due time, stores a safe human-readable error/HTTP status and releases the lease while preserving every last-good MEET count. Stop and manual activation also advance the generation and invalidate in-flight leases. The current MATCH/GROW reset leaves MEET synchronization state, generation, leases, and timing unchanged. Abandoned dispatches and expired workers are stopped by a separate scheduler watchdog; there is no automatic recovery or replacement of an expired worker.

The 2026-10-21 local sync repair changes no schema or grants. The Edge function now withholds `complete_meet_sync` when the shared verification summary flags an unrelated event entrance or unknown participant status. It sends completed page/record progress to `fail_meet_sync` for post-fetch validation failures. That historical release did not alter the transaction boundary or lease logic; the newer event-controls migration supersedes its scheduling policy. Read-only hosted catalog checks confirmed RLS on the five sync/settings/aggregate tables, service-only execution of the three sync RPCs, and zero sync runs or leases. Transactional behavior was not rerun because this task was restricted to read-only hosted tests.

`record_meetings` and `record_feedback` verify the staff membership again in SQL. Their event/request-ID uniqueness and row locks make retries safe under concurrent calls. They insert individual records and update the aggregate in the same transaction. The aggregate constrains rating sums to the 1–5 range implied by the feedback count. The schema defaults the meeting target to null; the client confirmed 1,200 on 2026-10-15, and only `event_settings.meeting_target` was set to 1,200 for event 17135. The actual completed-meetings aggregate was not changed by that setting update.

`20261015204348_audit_controller_reversals.sql` adds the reversal audit table, a recent-request index, and service-only `reverse_controller_action` / `list_controller_actions` RPCs. A reversal locks its original request, checks staff membership and retained individual records, subtracts the full original quantity or rating contribution atomically, then inserts one uniquely keyed audit row. Exact retries return the existing reversal; another correction for that action fails. Ordinary reversals retain original requests and meeting/rating records. Only `dashboard_aggregates` remains in the Realtime publication.

The authorized browser integration test on 2026-10-16 began with one previously documented synthetic request. Its audited reversal set the aggregate to 0 without deleting the original. A new +1 browser submission then produced aggregate 1, two meeting records, two unique request IDs, and one reversal. Retrying the new request ID through `record_meetings` left those counts unchanged. The Controller reversed the new action, returning the aggregate to 0 with two retained meeting rows and two reversal rows. The owner separately approved **test fixture cleanup**: a guarded transaction, first dry-run with `ROLLBACK`, removed only those exact two verified synthetic requests, meeting rows, and reversal rows. A fresh hosted read confirmed aggregate 0, target 1,200, zero controller requests/meeting records/reversals/feedback, zero sync runs/MEET snapshots, and one retained membership. The cleanup was exceptional test-only deletion; normal undo remains audited and retains records.

The hosted transaction verification in `supabase/verification/database_transactions.sql` creates synthetic Auth identities and records, simulates member RLS reads and direct-write denial, checks service-only RPC grants and aggregate-only publication, then exercises meeting/rating idempotency and MEET lease/atomic-publication/failure behavior. It ends with `ROLLBACK`; a separate read-only query confirmed zero synthetic users, memberships, records, snapshots, runs, and leases afterward. It does not prove simultaneous cross-session races or Realtime websocket delivery. The linked public-schema lint found no errors.

The approved b2match dry run used only `verify-b2match`, which has no database client. A read-only hosted query after its complete five-page API traversal confirmed zero MEET snapshots, sync runs, and leases, with all MEET display columns still null. The API-derived counts were not published.

On 2026-10-16, after the owner confirmed portal parity, `supabase/verification/publish_portal_snapshot.sql` published the approved 202 registered / 0 checked-in aggregate in one guarded transaction. It inserted one aggregate-only `meet_snapshots` row, updated the MEET fields in `dashboard_aggregates`, and set `event_settings.meet_verified=true`. The transaction was previewed with `ROLLBACK`; a fresh hosted read after commit confirmed one snapshot and zero sync runs or leases. No participant or canceled-person record was stored. The existing `last_successful_sync` column holds the **manual publication time** for this snapshot; while automatic sync is disabled, the API calls that timestamp `publishedAt`. This does not indicate a new API synchronization.

The security migration conditionally revokes `EXECUTE` on the pre-existing `public.rls_auto_enable()` from `PUBLIC`, `anon`, and `authenticated`. It does not remove the `ensure_rls` event trigger or alter application tables. After deployment, hosted grant checks found `anon` and `authenticated` could not execute the helper and the trigger remained enabled; `service_role` retained access to the new correction RPCs while browser roles did not.

Retention is not yet approved. The current schema retains safe aggregate snapshots, sync metadata, and staff action records until an owner-approved retention and deletion procedure is set. Before production release, run full security/performance advisors with project access, test simultaneous sessions and Realtime delivery, and rehearse backup and rollback. Never reset a hosted database to test this migration.

## Event controls and synchronization migrations

The initial audit on 2026-10-28 confirmed that hosted project `kkiambvltxuieuncwtfz` had only the initial, RLS-helper, reversal and map migrations. `get_checkin_control`, `record_manual_checkin` and both manual control tables were absent; the frontend's check-ins view therefore could not load. At that audit the effective values were MEET 202/0, MATCH 7, GROW 2 with rating sum 7. These are observed aggregate values, not proof that records are event-day production or test submissions.

The release prepares these migrations in order; deployment status must be confirmed against hosted migration history:

1. `20261023172257_manual_checkin_fallback.sql` establishes the existing manual-control/session and historical reconciliation structure.
2. `20261028192045_event_operations_and_sync.sql` supersedes its reconciliation behavior with a one-way manual transition, adds durable synchronization control and immutable operations, and exposes only safe aggregates for public Realtime.
3. `20261028192319_b2match_server_schedule.sql` enables `pg_cron`/`pg_net` and installs a private fixed-destination Vault dispatcher plus an idle scheduler/watchdog. Applying the migration does not start synchronization or fetch B2Match.
4. `20261028211842_reset_match_grow.sql` supersedes only the earlier reset scope: the protected operation clears MATCH and GROW while preserving MEET and synchronization. Its application status belongs in the deployment record; creating the migration is not evidence of deployment.

`get_event_control(event, actor)` returns the current role, effective totals, source, version, target, override, API measurements, attempt/success/next timestamps and safe failure information. `get_checkin_control` supplies the existing expandable controller, including version, manual fallback and admin-only exact-total eligibility. Both require staff/admin membership inside SQL. `event_settings.meeting_target` remains the single target source.

`admin_event_operation` requires an admin membership, request UUID and expected version. `start_sync` persists Starting and immediately enqueues a worker; `stop_sync` fences the current generation and preserves counts. `activate_manual` requires sync already stopped/failed, creates a manual session and permanently prohibits Start Sync or reconciliation for this operating session. `update_settings` atomically validates exact registration overrides and a positive meeting target. Registration overrides are available independently of source mode, cannot fall below checked-in, and remain distinct from raw API snapshots. Later API publication retains the override as the effective registered count; publication is rejected if API check-ins exceed that effective capacity. Manual Mode remains required for manual check-in changes. Changing a target updates the aggregate notification timestamp without changing meeting records. Exact retries return the original receipt, while a reused UUID with different input fails.

`record_manual_checkin` permits only +1/+2/+5/+10 in already activated Manual Mode and validates staff/admin membership. `set_manual_checkin` requires admin membership and an expected control version; it replaces the effective checked-in count exactly. Both enforce nonnegative integer/capacity constraints and commit before success. Exact replacement starts a new baseline/session so an earlier increment cannot later subtract from that corrected total. Undo reverses the complete quantity of a specific eligible increment. The control-row lock serializes all source, override, increment, exact-total, reset and reversal operations. Request UUID collisions across submissions, reversals and admin operations are rejected, while exact same-action retries return the retained receipt. MATCH and GROW submissions acquire the same lock before their existing idempotent record/aggregate transaction, ensuring reset and concurrent submissions have a consistent order.

`reset_event` requires an admin, a current expected version, and `p_value` containing both the exact confirmation `RESET EVENT` and `scope:"match_grow"`. The same scope is mandatory in the Edge request; older cached clients lacking it must be rejected before mutation. No new endpoint or public write grant is added. In one transaction it sets only the effective MATCH/GROW counters to `completed_meetings=0`, `feedback_count=0`, and `rating_sum=0`, marks event meeting/feedback requests with `cleared_at`, and records before/after audit values. The derived average is `null` when the feedback count is zero; ratings remain integer 1–5 records, and the reset does not create a zero-star rating.

The reset preserves individual meeting and feedback records, requests, reversals, MATCH target, accounts, configuration, unrelated events, and historical audit. Cleared meeting/feedback requests cannot be undone or replayed into a new total. A future aggregate rebuild must join **both** meeting and feedback records to their requests and exclude `cleared_at IS NOT NULL` and reversed requests. New distinct meeting/rating submissions remain valid after reset.

MEET registered/check-in counts and check-in rate, registration override, source/mode, manual session, API enabled/state/generation and attempt/success/next timestamps, snapshots, sync runs/leases, and check-in requests/Undo/history remain unchanged by reset. The operation does not start, stop, fence, or republish attendance synchronization. Concurrent authorized attendance changes retain their normal behavior; the reset does not suppress them. Live reset remains a separate owner action and is not a deployment or smoke-test step. The earlier October 28 MATCH/MEET reset behavior is superseded; dated evidence above records historical operations rather than the current reset contract.

`controller_operations` records Start, Stop, manual activation, settings, exact totals and reset with actor, request UUID, input, before/after values and timestamp. `list_controller_actions` merges these with submissions/reversals and retained historical reconciliations; destructive reset is never offered as undoable. Browser roles have no read/write privileges on this table or `meet_checkin_control`.

The scheduling migration uses `event_private.dispatch_meet_sync()` and `event_private.tick_meet_sync()`, with a fixed event/function URL and the `nh_b2match_worker_secret` Vault entry. A restricted readiness helper returns only whether the credential and active cron job exist; Start Sync stays disabled until both are present. The dispatcher is a restricted `SECURITY DEFINER` only because the service-role admin RPC must enqueue a Vault-authenticated HTTP request; it accepts no URL, secret or event from its caller. Only `service_role` may invoke it; the tick is callable only by the database owner. The cron tick wakes every ten seconds, dispatches only due enabled API work, and records the dispatch to prevent duplicates. Due times are measured 120 seconds from each claimed start, with up to ten seconds scheduler latency and no catch-up. An active lease blocks overlap. An invocation not claimed within 30 seconds, a failed transport response, or an expired 150-second worker lease moves the event to Failed and disables further dispatches. No secret is stored in migration SQL or returned by a controller RPC.

Rollback must preserve the new control/audit rows and current aggregate values. Stop synchronization first. Reverting frontend/Edge artifacts can leave additive columns/tables in place; do not drop applied migrations or delete historical rows. A database behavior rollback requires an owner-reviewed forward migration and explicit data-preservation plan.

## Isolated verification

`supabase/verification/manual_checkins.sql` rejects any database with existing app memberships/requests/snapshots, creates synthetic identities, and rolls back all fixtures. It checks admin/staff boundaries, browser grants, complete publication, cadence, overlap, failure-stop, stop fencing, one-way manual activation, all increment quantities, duplicate UUIDs, exact-total version conflicts, registration capacity, target changes, undo and reset preservation/history. `supabase/verification/sync_schedule.sql` additionally requires a mock-only transport marker before exercising immediate dispatch, no duplicate dispatch, due-time gating, lost-worker/transport watchdogs and manual-mode idleness. Never execute either against the live event. `supabase/verification/run_isolated.mjs` is the portable in-memory runner. It requires the pinned test runtime `@electric-sql/pglite@0.3.14`, optionally resolved from `NH_PGLITE_RUNTIME`; it accepts no database URL and replaces network/scheduler interfaces with synthetic SQL fixtures. The earlier readiness versions of these scripts passed with isolated PGlite PostgreSQL and synthetic transport; that evidence predates the MATCH/GROW scope correction. Current reset verification belongs in the testing/deployment records. Hosted extension installation, idle Cron execution and authenticated stopped-worker delivery through pg_net were subsequently verified; see the deployment guide. True simultaneous new PostgreSQL sessions remain unverified.
