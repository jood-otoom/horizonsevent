## Client and counting rules

`supabase/functions/_shared/b2matchClient.ts` preserves the Phase 3 fixed HTTPS URL, manual redirect rejection, Bearer header from an Edge Function secret, runtime response validation, 50-item pages, opaque-token traversal, ID deduplication, repeated-token/page detection, empty/intermediate/inconsistent-page rejection, and all-or-nothing result. It rejects oversized pages and padded string identifiers rather than accepting ambiguous IDs. The known empty first-page `currentPage` string is accepted; missing, null, non-string, or whitespace-only nonempty labels fail. Missing, whitespace-only nonempty, or malformed next-page tokens fail. The deployed shared repair accepts an exact empty string `nextPageToken` only when the accumulated raw count equals the unchanged `totalItems`, the final page has fewer than the requested 50 items, and the number of distinct IDs equals the raw count; otherwise it raises `incomplete_pagination`. Existing `null` terminal-token handling remains unchanged, although `null` is not listed as the field's type in the official schema. Nonempty current-page labels are checked for repetition; empty labels rely on repeated-token detection, total/page consistency, and the page cap. It allows at most 100 pages and 120 seconds overall, with a 12-second per-request timeout. Network/429/5xx failures receive at most three attempts with backoff and jitter, respecting `Retry-After` within the budget. 401/403/404, malformed JSON, and contract errors fail without retries. The client returns safe page/record counts and an upstream request-attempt count, including retries. It never logs or persists participant records.

Its function has no database client call and no browser CORS. ## Manual fallback and recovery boundary (local code only)

The parsed participant response includes stable `id` strings, but the requested emergency `+1` control records no participant identifier. Participant-level matching of a manual action to a later b2match scan is therefore impossible with this UI. The local migration uses a manual session anchored to the last displayed count; each +1 is separate from a raw API `meet_snapshots` row. When the publishing sync is eventually approved and resumes, its complete raw counts are stored but are not added to, or automatically substituted for, an active manual count. Staff see the discrepancy in `/controller` and must verify the newer API count before an explicit source switch. This avoids silent overlap; it cannot prove that a staff tap represented a distinct person, so the operator must use +1 only for an entrance scan not yet reflected in the displayed count. A safe production rehearsal of this transition remains pending. The current sync gate and verifier gate remain disabled.
