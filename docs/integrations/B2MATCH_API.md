# b2match API integration

## Verified documentation and portal-confirmed snapshot

The owner supplied event ID 17135 and the [official participant API reference](https://api-docs.b2match.com/#tag/participants/operation/listParticipants). The [public b2match event page](https://www.b2match.com/e/new-horizon) embeds `Event:17135` with the title `New Horizons 2026`, confirming that the configured ID maps to the expected event name. The [official OpenAPI schema](https://storage.googleapis.com/b2match-docs/openapi.yaml) documents `GET https://api.b2match.com/public/participants`, Bearer authentication, `event_id`, a default `limit` of 50, opaque `page` tokens, and a string `pagination.currentPage`. It documents participant statuses `registered` and `canceled`; `checkIns` is an oldest-first history with `check_in` and `check_out`. `locationType="event"` with `locationId` equal to the event ID represents the event entrance; agenda locations use `locationType="location"` and a separate ID space. No polling rate limit was found in the accessible reference.

The first four owner-approved attempts failed before a complete page could be accepted. They identified an empty first-page `pagination.currentPage` string. The official schema requires a string but does not require a nonempty string, so the parser had rejected a documented type unnecessarily. The corrected verifier then completed a fifth, owner-approved all-pages dry run for event 17135: **203 raw records, 203 unique participants, 202 registered, 1 canceled, 0 checked in, 0%**, with 5 completed pages, 5 upstream requests, and 8,248 ms elapsed. No unexpected statuses, unrelated event-entrance check-ins, or agenda-location check-ins were found. The API response passed local structure and pagination checks; an empty `currentPage` label is now allowed while opaque tokens, page totals, and the page cap remain loop guards. The verifier response said `portalVerification: "pending"` at the time because it cannot read the portal. The owner confirmed portal parity on 2026-10-16 and approved publishing the 202/0 aggregate once. Actual new-registration/check-in propagation and permitted polling cadence remain unverified. The read-only verifier's gate was reset off; the publishing sync function remains disabled.

## Client and counting rules

`supabase/functions/_shared/b2matchClient.ts` preserves the Phase 3 fixed HTTPS URL, manual redirect rejection, Bearer header from an Edge Function secret, runtime response validation, 50-item pages, opaque-token traversal, ID deduplication, repeated-token/page detection, empty/intermediate/inconsistent-page rejection, and all-or-nothing result. Nonempty current-page labels are checked for repetition; empty labels rely on repeated-token detection, total/page consistency, and the page cap. It allows at most 100 pages and 120 seconds overall, with a 12-second per-request timeout. Network/429/5xx failures receive at most three bounded retries with backoff and jitter, respecting `Retry-After` within the budget. 401/403/404, malformed JSON, and contract errors fail without infinite retries. The client returns safe page/record counts and an upstream request-attempt count, including retries. It never logs or persists participant records.

`aggregateMeet` counts each unique event participant with status `registered` once; `canceled` is excluded, and any unknown status rejects the complete sync. `validated` and `visible` are not registration filters. The owner chose **ever checked in**: a registered participant counts once if any historical scan has `type="check_in"`, `locationType="event"`, and `locationId=17135`. Later check-outs do not erase historical attendance. Scans at unrelated agenda locations do not count. The rate is `round(checkedIn / registered * 100)`, with zero only after a confirmed empty full pull. The 202 registered / 0 checked-in totals match the portal; behavior for real scan and check-out changes still needs observation.

The client deliberately does not use `updated_since`. Its documented timestamp semantics can miss registration-answer-only changes, and incremental scans alone cannot reconcile removals. Every published total comes from a complete traversal. A failed or partial traversal never replaces the previous snapshot.

## Synchronization and freshness

`verify-b2match` is a separate, service-only, **non-publishing** path. It requires its own named secret key `b2match_verification`, an explicit disabled-by-default `B2MATCH_DRY_RUN_ENABLED` gate, the event ID setting, and the b2match secret. Its function has no database client call and no browser CORS. It uses the same complete fetch and counting rules, returns only aggregate counts and safe integer diagnostics, and measures API attempts and elapsed time. The response always labels portal verification as pending; a completed traversal alone does not establish portal parity. It returns null KPI values when unexpected statuses or scans at another event entrance appear. A failed pull returns no partial KPI. The deployed failure response returns an allowlisted failure class, a static field name, a fixed value-kind label, and safe progress counters to its authenticated caller. The dedicated invocation key exists, and the gate is disabled.

`sync-b2match` requires a named secret Supabase key `automations`, the disabled-by-default `B2MATCH_SYNC_ENABLED` gate, and a database lease. The named key is not configured; publishable-only and anonymous calls received generic 401 responses in hosted tests. It publishes via one transaction only after a complete validated traversal. The browser reads stored aggregates via `dashboard-data`; its 15-second read fallback is unrelated to b2match polling frequency. Supabase Cron configuration is prepared in documentation but no job is active. The default display freshness threshold is 300 seconds in `event_settings`; this is a placeholder to review against the approved cadence, not a claim that the API permits one-minute polling.

The owner-approved one-time publication used `supabase/verification/publish_portal_snapshot.sql` after a rollback-only preview. It stored **202 registered, 0 checked in, 0%** and set `meet_verified=true` at 2026-10-16 01:14:50 Asia/Amman. The canceled record was excluded from the registered count and is not sent to the display. This transaction used the already verified totals; it made no b2match request, created no `sync_runs` or lease, and did not enable the publishing function or Cron. While automatic sync is disabled, `dashboard-data` returns `status: "snapshot"` with `publishedAt`, and the UI says there are no automatic updates. The database's existing `last_successful_sync` column holds this one-time **publication time**, not a claim of a new API synchronization. A later approved sync can replace the snapshot with newly fetched values.
