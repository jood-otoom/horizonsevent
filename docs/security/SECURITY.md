## Access model

Demo mode is intentionally local and synthetic. Live mode is private: the frontend requires a Supabase Auth session and event membership before rendering dashboard/controller data. `dashboard-data` independently requires a valid user JWT and viewer/staff/admin membership; `controller-submit` requires staff/admin membership. Both user-facing functions now require the platform JWT check and a second `@supabase/server` user check. A membership lookup error returns a generic 503. SQL functions recheck staff membership, and request IDs plus database constraints enforce idempotency. `sync-b2match` accepts only the named Supabase secret API key `automations` and an explicit disabled-by-default sync gate. Its platform JWT check is disabled because the server key is supplied on `apikey`; the wrapper validates that named key. No function has `auth: 'none'`.

RLS is enabled on every new exposed table. Authenticated browser users can read only their own membership, their event's settings, and the aggregate display row for the private dashboard; the separate public `/map` aggregate is readable by `anon` and `authenticated`. Browser roles cannot write any table, read sync logs, read individual meeting/feedback records, or call service-only RPCs. `dashboard_aggregates` alone is published to Realtime. Realtime callbacks trigger a refetch instead of displaying arbitrary broadcast payloads. The 2026-10-14 rollback-only SQL test exercised grants, RLS, and publication membership. Separate hosted tests with disposable Auth users confirmed role-based function access, denied direct writes and sync RPCs, authorized Realtime delivery/reconnection, and no aggregate events for an unassigned user. Actual token expiry and a full production security rehearsal remain pending.

The deployed correction migration keeps `controller_reversals` private with RLS enabled and no browser grants. Its service-only, `SECURITY INVOKER` functions recheck staff membership, lock the original action, preserve records, and allow one audited reversal per original request. The Edge Function applies the same staff/admin check to history reads and corrections. Hosted grant checks confirmed browser roles cannot execute the correction RPCs; the authorized Controller successfully read action history and reversed two synthetic meeting actions before owner-approved fixture cleanup.

## Secrets and origin controls

`B2MATCH_API_KEY` was configured in hosted Edge Function secrets by the owner according to the earlier deployment record; its value has not been inspected or printed in this task. The b2match host/path is fixed HTTPS, redirects are rejected, and the production path uses the runtime's native TLS validation with no certificate-bypass setting in source. The Authorization header is Bearer, matching the referenced b2match OpenAPI contract. The Edge runtime's Supabase secret key stays server-side. Only `VITE_SUPABASE_URL` and a publishable key may enter the browser bundle. Never use a service-role/secret key in `VITE_*`, logs, tests, or Git. Local and hosted secrets must be separate.

## Data minimization and failure behavior

b2match participant IDs and scan histories are held only during a full sync. PostgreSQL stores aggregate snapshots and safe run metadata; no raw participant response or personal fields are persisted or returned. The controller stores only staff UUIDs and meeting/rating records needed for audit and correct averages. No participant data is sent to analytics. Errors reveal generic classifications; upstream bodies and Authorization headers are never logged by application code. A failed pull preserves the previous counts and marks them stale; the first failed pull never becomes a zero total.

The owner-approved manual publication on 2026-10-16 stored only 202 registered, 0 checked in, 0%, and a publication timestamp in the aggregate and one snapshot row. It did not store the canceled participant, perform another b2match request, or create a sync run or lease. The read-only `dashboard-data` endpoint still requires Auth and event membership and labels this value `snapshot` while automatic synchronization is disabled. The `automations` key and Cron schedule remain absent.
