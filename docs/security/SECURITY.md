# Security and privacy

## Access model

Demo mode is intentionally local and synthetic. Live mode is private: the frontend requires a Supabase Auth session and event membership before rendering dashboard/controller data. `dashboard-data` independently requires a valid user JWT and viewer/staff/admin membership; `controller-submit` requires staff/admin membership. Both user-facing functions now require the platform JWT check and a second `@supabase/server` user check. A membership lookup error returns a generic 503. SQL functions recheck staff membership, and request IDs plus database constraints enforce idempotency. `sync-b2match` accepts only the named Supabase secret API key `automations` and an explicit disabled-by-default sync gate. Its platform JWT check is disabled because the server key is supplied on `apikey`; the wrapper validates that named key. No function has `auth: 'none'`.

RLS is enabled on every new exposed table. Authenticated browser users can read only their own membership, their event's settings, and the aggregate display row. They cannot write any table, read sync logs, read individual meeting/feedback records, or call service-only RPCs. `dashboard_aggregates` alone is published to Realtime. Realtime callbacks trigger a refetch instead of displaying arbitrary broadcast payloads. The 2026-10-14 rollback-only SQL test exercised grants, RLS, and publication membership. Separate hosted tests with disposable Auth users confirmed role-based function access, denied direct writes and sync RPCs, authorized Realtime delivery/reconnection, and no aggregate events for an unassigned user. Actual token expiry and a full production security rehearsal remain pending.

The deployed correction migration keeps `controller_reversals` private with RLS enabled and no browser grants. Its service-only, `SECURITY INVOKER` functions recheck staff membership, lock the original action, preserve records, and allow one audited reversal per original request. The Edge Function applies the same staff/admin check to history reads and corrections. Hosted grant checks confirmed browser roles cannot execute the correction RPCs; the authorized Controller successfully read action history and reversed two synthetic meeting actions before owner-approved fixture cleanup.

## Secrets and origin controls

`B2MATCH_API_KEY` is configured in hosted Edge Function secrets by the owner; its value has not been inspected, printed, or placed in source. The b2match host/path is fixed HTTPS and redirects are rejected before credentials can be forwarded. The Edge runtime's Supabase secret key stays server-side. Only `VITE_SUPABASE_URL` and a publishable key may enter the browser bundle. Never use a service-role/secret key in `VITE_*`, logs, tests, or Git. Local and hosted secrets must be separate. The source includes no real key; this directory is not a Git repository, so tracked-history exposure cannot be audited.

`DASHBOARD_ALLOWED_ORIGINS` is an exact server-side browser-origin allowlist; this test deployment allows `http://127.0.0.1:5173` and `http://127.0.0.1:5176`. A hosted preflight on 2026-10-15 returned 204 for both allowed origins and 403 for `http://localhost:5176`, which is a separate origin. Only HTTPS origins are accepted otherwise, with HTTP loopback allowed for local development. Cross-origin requests from unapproved origins get 403 before handler execution; an approved origin receives a matching CORS response. Requests without an Origin still require Auth or the named service secret. An anonymous GET from the newly allowed origin still returned 401. CORS is not authentication. Restrict frontend hosting and Supabase project operators to approved personnel before production. The sync wrapper now returns generic 401 when its named key is absent; a hosted test found that the SDK otherwise disclosed configuration details in a 500 response. All sync 5xx responses are sanitized.

## Data minimization and failure behavior

b2match participant IDs and scan histories are held only during a full sync. PostgreSQL stores aggregate snapshots and safe run metadata; no raw participant response or personal fields are persisted or returned. The controller stores only staff UUIDs and meeting/rating records needed for audit and correct averages. No participant data is sent to analytics. Errors reveal generic classifications; upstream bodies and Authorization headers are never logged by application code. A failed pull preserves the previous counts and marks them stale; the first failed pull never becomes a zero total.

The owner-approved manual publication on 2026-10-16 stored only 202 registered, 0 checked in, 0%, and a publication timestamp in the aggregate and one snapshot row. It did not store the canceled participant, perform another b2match request, or create a sync run or lease. The read-only `dashboard-data` endpoint still requires Auth and event membership and labels this value `snapshot` while automatic synchronization is disabled. The `automations` key and Cron schedule remain absent.

## Before release

### Prepared read-only verification boundary

`verify-b2match` is deployed under the owner's separate approval, with its `B2MATCH_DRY_RUN_ENABLED` gate-reset command reporting success after the completed fifth dry run. It uses its own named secret key `b2match_verification`, disabled browser CORS, and no database calls. Its handler accepts only POST, reads the b2match key from Edge Function secrets, and returns aggregate primitives after a complete pull. The shared named-key wrapper masks missing-key, authorization, arbitrary server, and exception details; an anonymous hosted POST returned generic 401 and a dedicated-key GET returned 405. Four diagnostic POSTs returned no counts; the fifth completed all pages and returned only aggregates and safe counters. The deployed failure response permits only fixed classifications, static field names, fixed value kinds, and safe progress numbers. No raw upstream content, participant identifier, or credential was returned. A read-only hosted query after the dry run found zero MEET snapshots, sync runs, and leases and null MEET dashboard columns. The invocation key was used only in process memory and never printed or stored. The publishing `sync-b2match` function remains disabled and was not redeployed with the corrected parser. A CLI attempt to inspect the dry-run gate value was rejected by automatic approval review because the command reads all Edge secret values into memory; no workaround was used. The cleanup command reported resetting the gate to `false`, though its value was not independently reread.

The owner-approved `20261014201641_restrict_rls_auto_enable_execute.sql` migration removed inherited `EXECUTE` access for `PUBLIC`, `anon`, and `authenticated` while leaving the postgres-owned DDL event trigger intact. Hosted post-deployment grant checks found no browser-role execution and confirmed the trigger remained present and enabled. A direct privileged invocation was not attempted.

Test direct `anon` and authenticated role access, service-only RPC grants, function JWT/secret rejection, event boundaries, Realtime row visibility, and browser bundle contents. Set a retention/deletion policy for aggregate history, sync logs, and staff records; confirm backups, key rotation ownership, session expiry, incident response, and rollback. Further use of the hosted b2match credential needs owner approval for each dry run; production sync and release need separate approval.

The 2026-10-14 hosted CLI Security Advisor reported two warnings for the pre-existing `public.rls_auto_enable()` event-trigger helper: `anon` and `authenticated` inherited its default `EXECUTE` grant. It is `SECURITY DEFINER`, has an explicit `pg_catalog` search path, and is attached to the `ensure_rls` DDL event trigger, where it enables RLS on newly created public tables. It was created by the project's automatic-RLS setting, outside the application migration. No application endpoint invokes it. The owner-approved grant migration subsequently revoked the browser-role execution grants; hosted `has_function_privilege` checks confirmed the restriction and the trigger remained enabled. Direct invocation was not attempted. The application migration revoked browser access to its service RPCs and enabled RLS on all application tables. The connected Advisor tool denied permission during the earlier review; a post-migration Advisor rerun remains pending.
