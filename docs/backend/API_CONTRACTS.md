# Backend API contracts

All functions live under the Supabase Functions URL `/functions/v1/<name>`. The deployed `public-dashboard-data` function has `verify_jwt=false` and `@supabase/server` `auth: none`; it accepts anonymous GET because its response is deliberately public and aggregate-only. The platform's `verify_jwt=true` check still applies to `dashboard-data` and `controller-submit`; `@supabase/server` then verifies the user JWT and supplies an RLS-scoped client. The service-only `sync-b2match` and deployed, disabled-by-default `verify-b2match` use named secret keys on `apikey`; both have `verify_jwt=false` and enforce their named key in the server wrapper. `DASHBOARD_ALLOWED_ORIGINS` now includes the exact `https://horizonsevent.pages.dev` origin alongside the two approved loopback origins; the public reader also retains its function-local exact-origin allowance. CORS is an extra browser boundary, not a substitute for Auth. Approved-origin OPTIONS requests return 204 with the requesting origin, allowed methods, and `authorization, apikey, x-client-info, content-type, x-retry-count` headers. Function-generated error responses retain matching CORS headers. Responses use `Cache-Control: no-store` where the browser calls them. Event ID 17135 is fixed server-side.

## `GET public-dashboard-data` — deployed public display aggregate

Anonymous GET for the fixed event 17135; OPTIONS is handled by the exact-origin CORS wrapper. Every other method returns 405. Both `/` and the signed-in `/controller` statistics read this endpoint with only `VITE_SUPABASE_PUBLISHABLE_KEY` on `apikey`, without a user JWT or credentials. The function uses server-side `ctx.supabaseAdmin` for two fixed, selected-column reads from `dashboard_aggregates` and `event_settings`; it never exposes either table through anonymous Data API grants. It reuses `makeDashboardPayload`, including MEET verified/snapshot/stale semantics and the average from `rating_sum / feedback_count`. The response shape is exactly the safe display contract below; no raw rating records, participant data, staff history, secret, or internal sync metadata is returned. Query, missing-row, and validation failures return only `{ "error": "data_unavailable" }` with 503. Responses are `Cache-Control: no-store`. This is a public endpoint even for non-browser callers; CORS is not an authentication boundary.

## `GET dashboard-data`

Retained for authorized clients, but the frontend no longer invokes it for `/` or `/controller` statistics. Requires a signed-in `viewer`, `staff`, or `admin` event member. A failed membership lookup returns a generic 503. It reads the RLS-scoped `dashboard_aggregates` and `event_settings` rows and returns only:

```json
{
  "eventId": 17135,
  "meet": {
    "registered": 10,
    "checkedIn": 7,
    "checkInRate": 70,
    "lastSuccessfulSync": "2026-10-10T10:00:00Z",
    "verification": "pending",
    "status": "pending"
  },
  "match": { "completedMeetings": 3, "targetMeetings": null },
  "grow": { "feedbackCount": 2, "averageRating": 4.5 }
}
```

Numbers and timestamp above are synthetic contract examples. Before the first MEET publication, `meet` is `null`, never a fabricated zero. MEET `live` requires a fresh successful automatic sync and the owner-approved portal-verification flag; a failed or aged synced snapshot returns `stale`. While `B2MATCH_SYNC_ENABLED` is off, an approved one-time publication instead returns `status: "snapshot"`, `verification: "approved"`, and `publishedAt` in place of `lastSuccessfulSync`. For event 17135 this currently carries 202 registered, 0 checked in, and 0%; the canceled participant is excluded and is not exposed. `publishedAt` is the database publication time, not a new b2match fetch time. A null meeting target means owner approval is pending. The response contains no participant or staff records.

## `POST controller-submit`

Requires a signed-in `staff` or `admin` event member. A failed membership lookup returns a generic 503. JSON body is either `{ "eventId": 17135, "kind": "meeting", "requestId": "<UUID>", "quantity": 1|2|3 }` or `{ "eventId": 17135, "kind": "feedback", "requestId": "<UUID>", "rating": 1..5 }`. A request ID may be retried with the same kind and payload; conflicting reuse returns 409. One meeting record is stored per meeting, including a +2 or +3 submission. Feedback stores each rating. The response includes a minimal `record` (`id`, `createdAt`, optional `rating`) and authoritative `stats` (`completedMeetings`, `feedbackCount`, `averageRating`). Database constraints and service-only transactional functions enforce idempotency and aggregate updates.

The deployed correction contract accepts `{ "eventId": 17135, "kind": "undo", "requestId": "<new UUID>", "originalRequestId": "<prior submission UUID>", "reason": "duplicate"|"wrong_count"|"wrong_rating"|"other" }`. The local one-click Controller sends `other` automatically because it does not ask the operator for a reason. It reverses the **entire** chosen submission, never an arbitrary numeric total. The same correction request can be retried; a second correction for the original returns 409. Success returns `reversal` (`id`, `originalRequestId`, `createdAt`) and authoritative `stats`. Normal corrections retain original meeting/feedback records; `controller_reversals` records actor, reason, and time. The hosted Controller reversed two synthetic meeting actions before the separately approved fixture cleanup.

## `GET controller-submit` — staff history

After the same staff/admin Auth and membership checks, returns `{ "actions": [...] }` with the five most recent combined operations in the pending local version; the hosted function still returns 12 original submissions. Each action contains request ID, kind, quantity or rating, creation time, and nullable reversal time. It exposes no staff identity or participant data. The browser has no direct read grant on the source or audit tables. The deployed route loaded and refreshed history in the authorized Safari rehearsal.

## `POST sync-b2match`

Requires the named Supabase secret API key `automations` in the `apikey` header. No browser route or user JWT can invoke it. If the named key is absent, it returns a generic 401 before the SDK can expose configuration diagnostics. It also requires `B2MATCH_SYNC_ENABLED=true`, `B2MATCH_EVENT_ID=17135`, and a server-side `B2MATCH_API_KEY`. It claims a database lease, fetches all pages, applies the same status and unrelated-event entrance-scan review as `verify-b2match`, then calls one transactional publication function only for complete acceptable data. A concurrent run returns 409; disabled or unavailable service state returns a generic 503; a failed pull or validation returns a generic 502 and leaves prior counts intact. Failed post-fetch validation sends full page/record progress to `fail_meet_sync`. Success returns safe page and record counts only. The repaired source was deployed as v20 on 2026-10-21 and verified by a read-back; its publishing behavior has not been exercised against the real API. The sync gate remains disabled and there is no scheduled job.

## `POST verify-b2match` — deployed, dry-run gate disabled

Requires a separate named Supabase secret API key `b2match_verification` in `apikey`, `B2MATCH_DRY_RUN_ENABLED=true`, `B2MATCH_EVENT_ID=17135`, and the server-side `B2MATCH_API_KEY`. Browser CORS is disabled. It calls only the fixed b2match participants API and never calls Supabase database APIs. On a complete traversal it returns `status`, `portalVerification: "pending"`, `eventId`, `registered`, `checkedIn`, `checkInRate`, `pagesProcessed`, `recordsProcessed`, `uniqueParticipants`, `requestsMade` (including retries), `durationMs`, and integer diagnostics for canceled records, unexpected statuses, other event-entrance scans, and agenda-location scans. `status: "complete"` means the API traversal completed, not that portal totals agree. Unexpected statuses or other event-entrance scans make all KPI values null and set `needs_review`. It returns no participant IDs, status strings, check-in history, or credential. A failed pull returns HTTP 424 with an allowlisted `error` class, optional static `field`/`observedKind` labels, request/page/record counts, duration, and null KPIs; arbitrary server errors remain generic. The 2026-10-16 owner-approved attempt returned 202 registered and 0 checked in, later confirmed in the portal and published as a static snapshot. A separate, single read-only POST on 2026-10-21 returned 230 registered, 14 canceled, 0 checked in, and `portalVerification: "pending"`; current portal parity is unconfirmed and the gate was restored off. That response used the older, less strict verifier parser. A later owner-approved code-only verifier deployment aligned its pagination and identifier validation with the publisher; the entrypoint, named-key authentication, counting rules, and disabled gate were unchanged. The subsequent single approved strict verifier POST returned HTTP 424 `invalid_response` for an empty `pagination.nextPageToken` after four accepted pages / 200 records. It returned no counts or warning diagnostics, and the gate was restored off. The live API response therefore fails the same parser used by the publisher; no publication is authorized.

The local shared-client candidate accepts an exact empty next token only after stable-total, short-final-page, and unique-ID checks. It changes no endpoint, authentication, response shape, counting rule, or database write path. Both deployed functions still use the older strict bundle until separately approved code-only releases; no live request has exercised the candidate.

## Errors and source labeling

Function errors expose short classifications, never upstream response bodies, keys, raw participants, or database internals. The frontend validates aggregate responses again. Demo mode calls none of these functions. In live mode a failed first public read shows unavailable values; a failed later read retains prior values with stale labels. The public dashboard polls every 15 seconds and refetches on browser reconnection. It no longer subscribes to the event-member-only aggregate Realtime publication. The controller retains its authenticated aggregate read and protected mutation paths.

## Startup map data boundary

The redesigned local `/map` route does not call a backend endpoint. `scripts/prepare_map_dashboard_data.py` validates the private `Map master` worksheet and writes aggregate-only `frontend/src/data/mapSnapshot.json` at build time. The browser bundles only the national and eight-governorate counts, category totals, source hash, and warning counts. Changing selection filters the bundled aggregate in React state and does not issue another request. See [the workbook integration guide](../integrations/MAP_WORKBOOK.md) for the source contract and regeneration command. The `/` and `/controller` API contracts are unchanged.

The earlier `/map` implementation read `public.map_dashboard_snapshots` through a Supabase Data API SELECT for event 17135. That aggregate-only row remains in the controlled test project with its previously verified RLS: `anon` and `authenticated` can SELECT, browser roles cannot write. The hosted row contains the historical 266-startup snapshot (150 Acceleration, 92 Go to Market, 24 Grow+). It was not updated, deleted, or synchronized by this redesign. The frontend `mapService` reader and its cache were removed because the new route no longer consumes that row. A future decision to replace or retire the hosted row needs separate review; the database migration and seed are retained as applied history.

## Pending local check-in contract

The updated `controller-submit` retains the same user JWT, staff/admin membership, origin allowlist, and fixed event ID. `POST` accepts `{eventId:17135,kind:"checkin",requestId:"<UUID>"}` for one increment, or `{eventId:17135,kind:"reconcile_checkins",requestId:"<UUID>",expectedManual:<integer>,expectedApi:<integer>,expectedApiAt:"<ISO instant>"}` for an explicit source switch. The latter succeeds only against the latest newer API snapshot and the counts the staff member reviewed. Both return `{record:{id,createdAt},checkins:{mode,registered,checkedIn,apiCheckedIn,apiAsOf,canReconcile}}` after persistence. A lost response is retried with the same ID. `GET controller-submit?view=checkins` returns `{checkins:...}` for staff. The default `GET` returns the latest five combined submissions, reversals, and source switches with `operation`, `kind`, creation time, relevant values, and `undoEligible`; only the current manual session's unreversed +1 check-ins may be undone. Existing meeting/feedback POST and undo contracts remain unchanged. API error responses remain generic 400/403/409/503 classes.

Both `dashboard-data` and the deployed `public-dashboard-data` return the existing aggregate contract: `meet.checkedIn` is the effective displayed count. Raw API counts are visible to staff through the pending check-in control, not the public response. No new frontend environment variable or public write grant is introduced. The manual-check-in contract above remains local code only; the hosted controller still has its prior contract until a separately approved rollout.
